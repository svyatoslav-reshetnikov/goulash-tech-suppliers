# Поиск поставщиков продуктов питания

Тестовое задание Goulash.tech (AI Generalist / AI Automation Specialist). Это рабочий прототип, не готовый продукт.

**Демо-стенд:** https://goulash.svyatoslav-reshetnikov.ru (вход по логину и паролю, их присылает автор).

## Что это и зачем

Закупщику сети суши и пиццы нужно найти поставщика, например, моцареллы в Казани. Обычно это час ручной работы: поиск, десяток сайтов, поиск телефонов и условий, таблица в Excel.

Этот сервис делает черновую работу сам:

1. Вы выбираете **продукт** и **город или регион** (можно с соседними регионами).
2. ИИ-агент ищет поставщиков в Яндексе, заходит на их сайты и читает нужные разделы: контакты, о компании, доставка, прайс, сертификаты.
3. Через 5–30 минут (агент изучает всех найденных кандидатов) вы видите **карточки поставщиков** с контактами, условиями и оценкой, кому звонить в первую очередь.

Главное отличие от «просто спросить ИИ»: **каждый факт в карточке подтверждён цитатой с сайта и ссылкой на страницу**. Цитату программа ищет на странице дословно, а значение сверяет с цитатой: телефон, email и ИНН по цифрам, цены и минимальный заказ по числам и единицам, остальные поля по словам. Так отсекается выдумка рядом с настоящей цитатой («Татарстан» под цитатой «Москва и область»). Если модель исказила цитату (склеила два места страницы, «исправила» опечатку), программа подставляет дословный фрагмент той же страницы, который проходит те же проверки; факт, которого на странице нет, по-прежнему отклоняется. Проверка механическая, а не смысловая: значение, пересказанное другими словами, она может отклонить, а неудачно выбранную, но дословную цитату пропустить. Поэтому цитата всегда видна рядом с полем. Если на сайте чего-то нет, так и написано: «не найдено на сайте».

## Что получает закупщик

| Требование задания | Что сделано |
|---|---|
| Поиск по категории товара | Справочник из 176 категорий-ингредиентов (рис, лосось, нори, моцарелла…) с подсказками при вводе |
| Город или регион | Вся Россия: 89 регионов, 1102 города, переключатель «Включая соседние регионы» |
| Название, контакты, сайт, источник | Карточка: название, сайт, телефоны, email, адрес, чем занимается, ИНН. У каждого факта раскрывается цитата и ссылка |
| Помочь решить, с кем связаться | Оценка 0–100 с объяснением (товар 40, расположение 20, полнота данных 25, надёжность 15), метка региона (соседний и другой регион названы явно: «В соседнем регионе: Московская область»), предупреждения (почта не с домена сайта, регион неизвестен, нет ИНН). Поставщик, у которого на сайте не подтверждён искомый товар, не показывается вовсе. «Рекомендуем связаться» получает поставщик с известным регионом и телефоном. Компактные карточки (раскрываются стрелкой) или таблица с сортировкой, сравнение 2–4 поставщиков |
| Цена и минимальный заказ | Цена на искомый товар за единицу (например, «≈84 ₽/кг»), если строка неоднозначна, — пометка «Уточните цену»; минимальный заказ одной строкой с единицами |
| Работа с результатами | Выгрузка в Excel (xlsx; запасной вариант CSV), дата сбора данных |
| Форма поиска | Один товар строго из справочника и место поиска |
| Плюсом: минимальный заказ, цена, сертификаты, доставка, регион работы | Собираются со страниц сайта. Нет на сайте — поле пустое с пометкой «не найдено на сайте» |
| Плюсом: заметки по поставщику | Поле заметки в карточке |

Кроме этого: живая лента шагов агента («Ищу в Яндексе…», «Читаю страницу…»), после запуска — очередь кандидатов (каждый найденный сайт с итогом: поставщик найден, товара нет на сайте, не подходит, сайт не открылся, не дошли), вкладка «История поисков» (результаты открываются без повторного запуска) и предупреждение «Такой поиск уже осуществлялся» с выбором: посмотреть прошлые результаты или начать новый поиск.

## Как это работает (простыми словами)

1. **Поиск.** Код сам перебирает места (город, регион, соседние регионы, у каждого свой код Яндекса), четыре формулировки запроса и две страницы выдачи; модель подключается после этого и может искать дополнительно. Затем загружаются главные страницы всех найденных сайтов и считается, сколько раз на них назван продукт (с синонимами): первыми изучаются сайты, где он встречается, последними — где не назван вовсе. Маркетплейсы, доски объявлений и каталоги-перепродавцы отсеиваются: нужны сами поставщики.
2. **Отсев.** Перед подробным изучением модель коротко смотрит главную страницу: продаёт ли компания нужный продукт бизнесу. Ресторан, розничный магазин или сайт о другом не изучаются и не сохраняются, деньги на них не тратятся. Не изучается и сайт, по главной странице которого неясно ни то, ни другое, а также сайт, на главной странице и в выдаче которого продукт не назван. Если неясно что-то одно или сама проверка не удалась, сайт изучается. Сайт, на котором после первого прохода продукт так и не назван, бросается после одного поиска по названию товара, не тратя поиски на недостающие поля.
3. **Изучение сайта.** Программа сама открывает главную, разделы «Контакты», «О компании», «Доставка», «Прайс», «Сертификаты» (подпись пункта меню важнее заголовка новости) и до двух страниц с названием продукта. Страница до 9000 символов уходит модели целиком, у длинной сохраняются начало, фрагменты про цены, доставку и сертификаты и конец с контактами. Языковая модель (YandexGPT) только выписывает из этих текстов нужные поля. Одностраничный сайт (все разделы — якоря на одной странице) читается одной страницей, и это не считается недостатком.
4. **Проверка.** Каждое поле принимается, только если цитата дословно есть на странице, значение следует из цитаты, телефон и ИНН прошли проверку формата и контрольной суммы.
5. **Добор недостающего.** Если, например, не нашлись цены или сертификаты, программа ищет их по сайту отдельными запросами и читает найденные страницы.
6. **Оценка.** Поставщики ранжируются обычным кодом, без ИИ: так оценка объяснима, воспроизводима и бесплатна. Совпадение с товаром (самая весомая часть) опирается на найденное подтверждение: товар есть в прайсе, в ассортименте или в описании; общие фразы вроде «полный ассортимент продуктов питания» дают лишь малую часть баллов. Цены и минимальный заказ разбираются из найденных строк тоже кодом, а не моделью.

Сайт, который не открылся или отвечает слишком медленно (страница ждётся до 45 секунд с одним повтором, на весь сайт отводится 7 минут), не ломает поиск: в ленте появляется пометка, агент идёт дальше. Поставщик, подробно изученный за последние 7 дней, берётся из базы без нового разбора сайта моделью. Результаты прошлого запуска не меняются от того, что нашли позже.

## Как быстро и сколько ресурсов

Контрольный запуск («Шампиньоны», Москва с соседними регионами, настройки по умолчанию): 24 минуты, 538 тыс. токенов, 18 запросов к поиску, 321 загрузка страницы, в очереди 51 кандидат, найдено 20 поставщиков (остановка по цели). Число изучаемых сайтов не ограничено заранее: изучается каждый найденный кандидат (до 60), поэтому поиск идёт 5–30 минут и тратит 150–800 тыс. токенов. До этой доработки тот же поиск находил 3 поставщика за 2,5 минуты.

Расходы ограничены в коде (`Limits` в `backend/app/agent/config.py`, не в `.env`): один запуск не потратит больше 800 тыс. токенов и 30 минут, поиск останавливается на 20 подтверждённых поставщиках, а запросы в Яндекс идут не чаще одного в 1,1 секунды. Не больше 10 запусков в сутки (`AGENT_MAX_RUNS_PER_DAY` в `.env`). В интерфейсе показан расход токенов; во что он обошёлся, смотрите в биллинге Yandex Cloud: своя оценка в рублях расходилась с настоящим счётом, поэтому её убрали.

Результат контрольного запуска: у большинства найдены контакты, адрес и минимальный заказ (например, «от 3 кг» у ГРИБ365 и Мастер Гриб); цен почти ни у кого нет (на сайтах они только по запросу), у части нет сертификатов или условий доставки. 8 из 51 сайта не открылись (часть недоступна и из браузера), 6 с наименьшей оценкой до изучения не дошли; для каждого в очереди видна причина.

## Показать быстро

Поиск идёт 5–30 минут, поэтому на показе удобнее открыть готовый результат во вкладке «История поисков», а новый запуск показать до появления первых карточек.

1. Откройте стенд, введите логин и пароль.
2. Вкладка «Справочник»: категории построены по реальному меню.
3. Вкладка «Найти поставщика»: выберите «Моцарелла», город «Казань», нажмите «Найти поставщиков».
4. Следите за лентой шагов агента. Карточки появятся по мере завершения поиска (5–30 минут); после запуска под лентой раскрывается очередь кандидатов.
5. Карточки свёрнуты: видны цена на товар, минимальный заказ, контакты и предупреждения. Стрелка справа раскрывает карточку, галочка «Показывать источники» открывает ссылки на страницы, откуда взяты данные. Телефоны и почты кликабельны.
6. Переключите «Таблица», отсортируйте по цене или минимальному заказу. Отметьте «Сравнить» у двух поставщиков и нажмите кнопку внизу: данные встанут рядом.
7. Добавьте заметку и нажмите «Скачать в Excel».

## Диагностика агента (eval)

В `backend/scripts/eval/` лежит вспомогательный прогон агента на наборе из 13 случаев «продукт × место». Это инструмент разработчика, а не измерение качества: эталонных списков поставщиков и верных значений полей в нём нет, поэтому он показывает не точность, а то, что нашлось и что пошло не так.

1. Прогон (платный: каждый случай — полноценный поиск на 5–30 минут): `python -m scripts.eval.run --yes` из каталога `backend`, нужные случаи выбираются через `--only`. Агент работает без базы приложения, история запусков не засоряется.
2. Отчёт (бесплатно): `python -m scripts.eval.score`. Сколько поставщиков найдено, у какой доли заполнены телефон, цена, минимальный заказ, доставка, регионы и сертификаты, сколько шло; ниже — какие сайты отсеяны или не сохранены и почему, какие поля отклонены (со значением) и какие были сбои поиска (с кодом и request-id).

## Развернуть на своём сервере

> ### ⚠️ Файл `.env` и ваш ключ — обязательно
> Файл `.env` **намеренно не лежит в репозитории**: в нём пароли и ключи. **Тот, кто разворачивает сервис, создаёт его сам и вписывает СВОИ ключи Yandex Cloud.** Без своего ключа поиск не заработает, а каждый запуск поиска оплачивается с аккаунта владельца ключа. Чужие ключи (в том числе автора) вам никто не передаёт.

Пошаговая инструкция для сервера на Ubuntu или Debian. Демо-стенд работает по этой схеме (HTTPS по домену, вход по паролю, выкладка из GitHub Actions). Шаги для чистого сервера (скрипт `setup-server.sh`, собственный Caddy с HTTPS) целиком на пустом VPS не прогонялись.

### Что понадобится

| Что | Зачем |
|---|---|
| Сервер (VPS) с Ubuntu/Debian, 2 ГБ памяти, публичный IP | Здесь будет работать сервис |
| Домен или поддомен | Нужен для HTTPS (сертификат выдаётся автоматически) |
| Аккаунт Yandex Cloud и платёжный аккаунт | Ключи для YandexGPT и Яндекс Поиска |
| Доступ к серверу по SSH | Подготовка и выкладка |

### Шаг 1. Направьте домен на сервер

В панели, где управляется DNS домена, создайте запись типа **A**: имя поддомена (например, `goulash`) → IP-адрес сервера. Подождите 5–30 минут и проверьте: `ping ваш.домен` показывает IP сервера.

### Шаг 2. Получите ключи Yandex Cloud

1. В консоли Yandex Cloud выберите каталог (folder) и скопируйте его идентификатор: это `YANDEX_CLOUD_FOLDER_ID`.
2. Создайте сервисный аккаунт и API-ключ с доступом к Yandex AI Studio (YandexGPT) и к Search API. Необходимые роли и области действия указаны в документации Yandex Cloud. Ключ идёт в `LLM_API_KEY`; отдельный ключ для поиска не нужен.
3. Убедитесь, что платёжный аккаунт активен: запросы платные.

### Шаг 3. Подготовьте сервер

Зайдите на сервер по SSH и подготовьте его скриптом из репозитория `deploy/setup-server.sh`. Он ставит Docker и rsync, создаёт пользователя `deploy`, папку `/opt/goulash` и открывает порты 22, 80 и 443. Скрипту нужен публичный SSH-ключ, которым потом будет заходить автоматическая выкладка (см. раздел про CI/CD; для ручной выкладки используйте свой ключ):

```bash
sudo bash setup-server.sh "ssh-ed25519 AAAA… комментарий"
```

Если Docker уже установлен, то же можно сделать вручную: любая папка для проекта и свободные порты 80 и 443.

### Шаг 4. Создайте файл `.env` на сервере

Возьмите шаблон `.env.example` и сохраните как `/opt/goulash/.env` на сервере (права `600`, владелец `deploy`). Заполните:

| Переменная | Что вписать |
|---|---|
| `POSTGRES_PASSWORD` | Любой длинный случайный пароль базы (внутренний, вручную не вводится) |
| `YANDEX_CLOUD_FOLDER_ID` | Идентификатор каталога из шага 2 |
| `LLM_API_KEY` | **Ваш** API-ключ Yandex Cloud из шага 2 |
| `LLM_MODEL` | Модель, например `yandexgpt-5-pro/latest` |
| `SITE_ADDRESS` | Ваш домен, например `goulash.example.ru`. Caddy сам получит HTTPS-сертификат |
| `WEB_PORT` / `HTTPS_PORT` | `80` и `443` |
| `AUTH_USER` | Логин для входа в сервис |
| `AUTH_PASSWORD_HASH` | Хеш пароля (команда ниже), **обязательно в одинарных кавычках** |

Хеш пароля получается одной командой на любой машине с Python 3 (пароль замените на свой, пробелов и одинарных кавычек в нём быть не должно):

```bash
python3 backend/scripts/hash_password.py 'ВАШ_ПАРОЛЬ'
```

Результат вида `pbkdf2_sha256$600000$…` вставьте в `.env` так: `AUTH_PASSWORD_HASH='pbkdf2_sha256$600000$…'`. Пароль в открытом виде нигде не хранится. Если `AUTH_PASSWORD_HASH` не задан, вход отключён и сервис открыт всем: удобно на своём компьютере, но для публичного сервера этого делать не стоит, запуски платные. Смена пароля сразу завершает все активные сессии.

### Шаг 5. Запустите

Разовый запуск вручную (дальше можно настроить автоматику, см. ниже). Скопируйте проект на сервер (например, `git clone` в `/opt/goulash`) и выполните в этой папке:

```bash
docker compose up -d --build
```

Первая сборка занимает несколько минут. Миграции базы и загрузка справочника категорий проходят сами. Через минуту откройте `https://ваш.домен`: откроется страница входа, введите логин и пароль.

### Как обновлять и что где лежит

- Обновить вручную: скопировать новую версию и снова `docker compose up -d --build`.
- Данные (база, сертификаты) хранятся в Docker-томах и переживают обновления и перезапуски. Полный сброс данных: `docker compose down -v`.
- Логи: `docker compose logs -f api`.
- Если сертификат не выдаётся: проверьте, что DNS-запись указывает на сервер, а порты 80 и 443 открыты.

### Если порты 80 и 443 уже заняты вашим обратным прокси

Бывает, что на сервере уже стоит Caddy, nginx или другой прокси на портах 80 и 443: второй веб-сервер на них не запустить. Тогда проект подключается к нему:

1. Проект запускается файлом `docker-compose.prod.yml`. Наружу он портов не открывает, а контейнер `web` подключается к Docker-сети вашего прокси (имя сети задаётся в `.env`: `PROXY_NETWORK`) под именем `goulash-web`. Вход по паролю проверяет само приложение (`AUTH_PASSWORD_HASH`), поэтому сайт закрыт, даже если в прокси ошиблись.
2. В конфигурацию вашего прокси добавляется домен, который он направляет на `goulash-web:80`. Для Caddy это блок `ваш.домен { reverse_proxy goulash-web:80 { flush_interval -1 } }`; `flush_interval -1` нужен, чтобы живая лента запуска доходила сразу, без буферизации.
3. Образы собираются не на сервере, а в GitHub Actions и хранятся в ghcr.io (раздел ниже). Если вы разворачиваете у себя, замените в `docker-compose.prod.yml` владельца образов `svyatoslav-reshetnikov` на свой.

Для отдельного пользователя на уже настроенном сервере есть скрипт `deploy/add-project-user.sh`: запускается один раз от root и больше ничего не трогает.

## Автоматическая выкладка (CI/CD)

В репозитории настроен GitHub Actions (`.github/workflows/ci.yml`):

- **При каждом push:** тесты бэкенда на настоящей базе Postgres и сборка интерфейса с проверкой типов.
- **При push в `main`**, если проверки прошли:
  1. на раннере собираются образы `goulash-api` и `goulash-web` и уходят в ghcr.io с тегом коммита (почему не на сервере: Docker Hub из России отдаёт образы нестабильно, а раннер GitHub тянет их без проблем);
  2. на сервер копируется только `docker-compose.prod.yml`, тег коммита записывается в `.env` на сервере, выполняются `docker compose pull` и `up -d` (файл `.env` с вашими ключами не перезаписывается);
  3. перед перезапуском выкладка ждёт, пока закончатся идущие запуски поиска, но не дольше 12 минут: они работают внутри `api`, оплачены, и перезапуск их оборвал бы. Запуск может идти до 30 минут, поэтому выкладка во время долгого поиска его оборвёт;
  4. проверяется, что страница входа открывается (200), а API без входа отвечает 401: значит, маршрутизация, HTTPS и защита работают.
- **Откат:** вернуть в `.env` на сервере прежний `IMAGE_TAG` и выполнить `docker compose -f docker-compose.prod.yml up -d`, пересборка не нужна.

Одноразовая настройка:

1. Создайте SSH-ключ только для выкладки: `ssh-keygen -t ed25519 -f goulash_ci -N ""`. Публичную часть (`goulash_ci.pub`) положите на сервер пользователю, под которым идёт выкладка (скрипты `deploy/setup-server.sh` или `deploy/add-project-user.sh` принимают её аргументом).
2. В репозитории на GitHub откройте Settings → Secrets and variables → Actions и добавьте секреты:

| Секрет | Значение |
|---|---|
| `SSH_HOST` | IP-адрес или домен сервера |
| `SSH_USER` | `goulash` (или `deploy` для чистого сервера) |
| `SSH_PRIVATE_KEY` | Содержимое файла `goulash_ci` (приватный ключ целиком) |
| `SSH_KNOWN_HOSTS` | Результат команды `ssh-keyscan ваш.домен` |
| `DEPLOY_PATH` | `/srv/goulash` (или `/opt/goulash`) |
| `SITE_DOMAIN` | Ваш домен, например `goulash.example.ru` |

3. Убедитесь, что на сервере уже лежит `.env` (шаг 4). Если его нет, выкладка остановится с понятной ошибкой, а не запустит сервис без настроек.

Ключи Yandex Cloud в GitHub **не хранятся**: они живут только в `.env` на сервере. Для скачивания образов сервер получает временный токен GitHub на время выкладки и выходит из реестра сразу после.

## Для разработчиков

**Стек:** Python 3.12, FastAPI, SQLAlchemy 2 (асинхронный), Alembic, Postgres 17; React 19, Vite, TypeScript, Tailwind; Caddy (раздача интерфейса, прокси `/api`, HTTPS); Docker Compose.

```
Браузер: React
   │
[web] Caddy ── статика, /api → api (SSE без буферизации), HTTPS
   │
[api] Python / FastAPI (один процесс)
   ├─ catalog/    справочник категорий: снимок, автозагрузка в пустую базу
   ├─ locations/  регионы, соседи, города, поиск по тексту
   ├─ auth.py     вход по паролю: сессия в подписанной cookie, защита всего /api
   ├─ agent/      цикл «модель — инструменты» и проверки (не знает про веб и базу)
   ├─ ranking/    оценка, метки расположения, объяснение, рекомендация
   └─ runs/       запуски в фоне, события, расход, сохранение поставщиков
   │
[db] Postgres
Снаружи: YandexGPT (AI Studio), Yandex Search API, сайты поставщиков
```

**Агент.** Сначала код сам ищет кандидатов по плану (`agent/discovery.py`: места × формулировки × страницы выдачи) и изучает их по очереди, пачками по пять сайтов. Затем подключается модель: она выбирает инструмент (`search_web`, `research_suppliers`, `finish`; `search_places` для 2GIS включается при наличии ключа) и может искать дополнительно, код выполняет вызовы и проверяет. Модели не доверяют: поле принимается, только если страница открыта в этом запуске и принадлежит сайту поставщика, цитата дословно есть в тексте страницы, значение следует из цитаты (числа и слова, телефон, ИНН). Лимиты шагов, времени, токенов и загрузок страниц заданы в коде. Загрузчик страниц защищён от обращений во внутренние адреса.

**Почему монолит.** Нагрузки нет (один пользователь, запуск от пяти до тридцати минут, узкое место — модель, сеть и квота поиска), команда одна, независимых релизов нет. Отдельный сервис для агента добавил бы второй образ и межсервисную отладку, но не улучшил бы поиск. Граница `agent/` чистая, поэтому его можно вынести в воркер с очередью в Postgres, когда понадобится масштабирование.

**Тесты.** 303 теста бэкенда (проверки данных агента, цикл агента на заглушках, оценка, цены и предупреждения на сохранённом результате реального поиска, экспорт, регионы, каталог, запуски на Postgres) и 40 тестов интерфейса.

```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt -c constraints.txt
pytest                       # без базы проходят 264 теста, остальные пропускаются
TEST_DATABASE_URL=postgresql+asyncpg://user@127.0.0.1:5432/suppliers_test pytest   # все 303

cd ../frontend && npm ci && npm test   # 40 тестов интерфейса (Vitest, нужен Node 22)
```

**Настройки оценки и поиска.** Веса оценки и баллы за подтверждение товара лежат в одном месте: `backend/app/ranking/config.py`. Лимиты запуска (токены, время, число поставщиков и сайтов, загрузки страниц) заданы в коде: `backend/app/agent/config.py`; в `.env` настраивается только суточный лимит запусков.

Версии зависимостей зафиксированы: `backend/constraints.txt` и `frontend/package-lock.json`.

**Структура репозитория**

```
backend/     FastAPI, агент, ранжирование, миграции, тесты, вспомогательные скрипты
frontend/    React-интерфейс, Caddyfile, Dockerfile
deploy/      скрипты подготовки сервера (setup-server.sh для чистого, add-project-user.sh для уже настроенного)
.github/     CI/CD (GitHub Actions)
certs/       публичные корневые сертификаты НУЦ Минцифры
docs/        SPEC.md (решения и результаты проверок по этапам), SUBMISSION.md (текст для HR)
```

Карта репозитория для разработчиков: [docs/notes-architecture.md](docs/notes-architecture.md); история изменений: [CHANGELOG.md](CHANGELOG.md). Подробные решения и результаты проверок по этапам: [docs/SPEC.md](docs/SPEC.md).

## Источники данных и лицензии

- Меню «Сушкоф и пицца» (eda1.ru): публичные страницы; использованы названия и описания блюд для построения справочника категорий.

- Данные о поставщиках берутся с их публичных сайтов во время запуска; к каждому полю сохраняются цитата и адрес страницы.
