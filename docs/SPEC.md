## 1. Цель

Сервис помогает закупщику найти и сравнить поставщиков продуктов питания (ингредиенты, готовая продукция, упаковка), собрать по ним ключевую информацию с указанием источников и решить, с кем связаться.

Целевой пользователь для демо: закупщик сети суши- и пицца-доставки («Сушкоф и пицца»). Он может искать поставщиков для текущих точек, у соседних регионов, а также для новой точки в новом регионе.

## 3. Функции

### MVP

1. **Каталог категорий**
   - при старте проверяет, загружен ли каталог; если нет, загружает автоматически;
   - кнопка «Обновить каталог»: новое добавляется, пропавшее архивируется;
   - индикатор в интерфейсе: число категорий, дата обновления, итог последнего обновления (+добавлено / −архивировано / ~изменено).
2. **Поиск**
   - выбор категории с автодополнением по справочнику (или свободный запрос, который LLM сопоставляет с категорией);
   - выбор города или региона из всей России, переключатель «включая соседние регионы»;
   - фильтр по типу поставщика (производитель, дистрибьютор, оптовик) — необязательный.
3. **Агент-исследователь** собирает кандидатов из нескольких источников, читает их сайты и заполняет карточки.
4. **Карточка поставщика**: название, сайт, описание и ассортимент, тип, регион и регионы доставки, контакты (телефоны, email, мессенджеры), ИНН и ссылка на ЕГРЮЛ.
   - Расширенные поля из ТЗ: минимальный заказ, примерная цена, сертификаты и документы, условия доставки.
   - Если поле не найдено, показывается «нет данных».
5. **Источники и цитаты.** У каждого поля есть ссылка на страницу и цитата, откуда оно взято. Цитата проверяется программно по тексту страницы.
6. **Живая лента шагов агента** («ищу в Яндексе», «читаю страницу доставки»).
7. **Ранжирование** с объяснением и метками локации: «в вашем регионе» → «доставляет в ваш регион» → «в соседнем регионе (какой)» → «неизвестно».
8. **Сравнение** 2–4 поставщиков в таблице.
9. **Рекомендация «с кем связаться»**: топ-3 с обоснованием и перечнем недостающих данных.
10. **Заметки по поставщику** (в ТЗ: «комментарии или заметки по поставщику»): свободный текст в карточке, хранится у поставщика и виден в любом запуске, где он найден; строка «Заметка» есть и в сравнении.

## 4. Архитектура

### Схема

```
Браузер: React SPA
   │ HTTPS
   ▼
[caddy]   раздаёт статику, проксирует /api/* → api
   ▼
[api]  Python, FastAPI (один процесс)
   ├─ routes/        HTTP + SSE
   ├─ catalog/       источник eda1.ru, синхронизация, вывод категорий
   ├─ agent/         агентный цикл и инструменты (не знает про FastAPI и БД)
   ├─ locations/     справочник регионов и городов
   └─ db/            репозитории
   ▼
[db]   Postgres

Исходящие запросы из api: LLM, Yandex Search API, 2GIS API, сайты поставщиков, eda1.ru
```

### Обоснование монолита (для README)

Нагрузки нет (один пользователь, запуск 30–90 секунд, узкое место — LLM и сеть, а не CPU). Команда одна, независимых релизов нет. Разделение на сервисы добавило бы второй образ, контракт между сервисами, дублирование моделей данных, передачу SSE через промежуточный слой и межсервисную отладку, но не улучшило бы главного критерия — качества поиска. Граница `agent/` сделана чистой: пакет принимает запрос и отдаёт поток событий, ничего не зная про веб и базу. Поэтому его можно вынести в отдельный сервис или воркер без переписывания. В разделе README «что в проде» описано, как это сделать: воркер на том же образе с очередью в Postgres (`SELECT ... FOR UPDATE SKIP LOCKED`), чтобы запуск переживал рестарт API.

### Запуск поиска (ход запроса)

1. `POST /api/runs` создаёт запись и запускает агента фоновой asyncio-задачей, в ответ возвращает `run_id`.
2. Браузер открывает `GET /api/runs/{id}/stream` (SSE).
3. Агент в цикле вызывает LLM и инструменты, каждый шаг пишется в `run_events` и уходит в SSE.
4. `save_supplier` пишет в базу поставщика с полями, цитатами и источниками.
5. В конце запускается ранжирование и объяснение, статус `done`.
6. События хранятся в базе, поэтому после обновления страницы лента восстанавливается, а запуск продолжается.

## 6. Каталог (источник и синхронизация)

### Источник: eda1.ru

Что известно (проверено на этапе 2):
- Сайт на Nuxt, меню отдаётся JSON-ом внутри HTML (`__NUXT_DATA__`). Отдельный API и браузер не нужны.
- 11 городов; список приходит в данных самой страницы (`delivery.citiesUrls`), а не прописывается вручную.
- Страница любого города целиком содержит меню этого города (`pinia.product.products`) и категории: **достаточно одного запроса на город** (11 запросов вместо сотен). Страница весит 2,4 МБ, со сжатием gzip около 300 КБ, поэтому загрузчик просит gzip (так обход укладывается в ~40 секунд, без сжатия — 2,5 минуты).
- Меню в городах различается (189–261 позиций в городе). Всего 409–415 уникальных позиций (число слегка меняется, меню живое). У одной и той же позиции название, описание и вес во всех городах совпадают (расхождений 0), поэтому объединение по id безопасно; счётчик расхождений всё равно ведётся в статистике.
- Отдельного поля «состав» нет: ингредиенты находятся в свободном тексте описания.
- `robots.txt` закрывает `/ajax/`, `/order*`, `/admin*` и служебные пути; меню не закрыто; паузы между запросами не задано.

Правила обхода: пауза не менее 1 с между запросами, честный `User-Agent`, только публичные страницы меню, не трогаем закрытые пути. Исключаем разделы-дубли `/samovyvoz` и `/novinki` при определении разделов позиции (список `IGNORED_SECTIONS` в `catalog/eda1.py`). Недоступный город не прерывает обход: он попадает в статистику, обход помечается неполным, архивация не выполняется.

**Для этапа 3.** В разделах позиций есть не только «Сеты», но и «Наборы» (36 позиций) и «WOW price»; описания сетов и наборов перечисляют названия роллов, а не ингредиенты, поэтому их разделы нужно пропускать при выводе категорий. У 13 позиций описание пустое: ингредиент берётся из названия (например, «Имбирь»).

### Правила синхронизации

- **Старт приложения.** После миграций проверяем: есть ли хотя бы одна успешная синхронизация и хотя бы одна активная категория. Если есть, ничего не делаем. Если нет, запускаем загрузку фоновой задачей, не блокируя старт. До готовности поиск недоступен.
- **Кнопка «Обновить».** Тот же код, что и первая загрузка.
- **Блокировка.** Одновременно идёт одна синхронизация (`pg_advisory_lock`). Повторный запуск возвращает 409.
- **Шаги:**
  1. sitemap → список городов;
  2. страницы разделов каждого города (последовательно, с паузой);
  3. объединение позиций по id с сайта (при расхождении берётся версия первого города в порядке обхода, при следующем обновлении может смениться);
  4. diff с базой: новые добавляются, изменённые обновляются;
  5. вывод категорий только для новых и изменённых описаний (раздел 7);
  6. архивация.
- **Мягкое удаление.** Позиция архивируется, если пропала изо всех городов. Архивируем **только после полного успешного обхода всех городов**: если какой-то город не скачался, позицию, которая есть только в нём, нельзя считать пропавшей. При частичном обходе только добавляем и обновляем, а итог помечается как неполный; кнопка «Обновить» докачает недостающее.
- **Защита от пустого результата.** Если после объединения позиций меньше половины от прежнего, синхронизацию отклоняем, данные не меняем, показываем ошибку.
- **Сбой извлечения категорий** не откатывает слой позиций; его можно перезапустить отдельно.
- **Мягкое удаление:** строка не стирается, а получает статус `archived` и пропадает из интерфейса. На неё могут ссылаться прошлые запуски поиска и шорт-листы, поэтому физическое удаление их бы сломало. Архивную запись можно вернуть.

## 6а. Фиксация каталога (снимок)

Решение для тестового задания: **каталог и справочник категорий не обновляются из приложения**. Однажды построенный и проверенный справочник хранится в репозитории и при развёртывании на другой машине попадает в базу автоматически.

- Файл `backend/app/catalog/seed/catalog_snapshot.json` (около 270 КБ): 15 групп, 176 категорий (с синонимами и происхождением), 409 позиций меню и 1410 связей позиций с категориями. Формат версионируется (`version`).
- **При старте** (`catalog/snapshot.py: ensure_loaded`): в базе нет активных категорий — снимок загружается за доли секунды (сеть и модель не нужны), в журнал пишется запись `trigger=snapshot`; категории есть — ничего не происходит. Импорт идемпотентен: повторный запуск не дублирует данные.
- **Проверено развёртыванием с нуля:** `docker compose down -v`, затем `up`: стек поднимается за ~17 секунд, справочник (176 / 409 / 1410) совпадает с исходным. Тест `test_export_then_import…` подтверждает, что экспорт после импорта воспроизводит снимок байт в байт.
- **Как пересобрать вручную (платно):** `python -m scripts.rebuild_catalog --yes` (обход сайта и разбор через модель), затем `python -m scripts.curate_catalog` (ручная правка) и `python -m scripts.export_catalog > app/catalog/seed/catalog_snapshot.json`. В приложении ни кнопки обновления, ни автоматической синхронизации нет; кроме того, пайплайн из раздела 6 остаётся в коде как офлайн-инструмент и покрыт тестами.
- **Ручная правка** (`catalog/curation.py`): список операций слияния, переименования, переноса и удаления, применённый к автоматическому черновику: 26 слияний, 8 переименований, 8 переносов, 1 удаление (блюдо «Пицца Сырная»). Результат: 203 → 176 категорий. Правка записана кодом, а не сделана «руками в базе», чтобы её можно было прочитать и повторить. Решения принимались без обращения к модели.

## 7. Категории (ингредиенты)

- Категория — каноническое название на уровне закупки, с родителем (например, «Рыба и морепродукты → Лосось»). Варианты написания хранятся как синонимы.
- Группы: `ingredient`, `packaging` (упаковка и расходники). Расходники из раздела «Дополнительно» (палочки и т. п.) попадают сюда автоматически; остальную упаковку (контейнеры, коробки для пиццы) добавляет ручной seed-файл `backend/app/catalog/seed/packaging.json` (группы лежат в `category_groups.json` рядом).
- **Вывод из описаний.** LLM получает описания и текущий справочник и сначала сопоставляет ингредиент с существующей категорией; новую создаёт, только если подходящей нет. Один вызов обрабатывает уникальные описания, а не позиции по всем городам.
- **Пропускаем** разделы `sety` и `combo`: их описания перечисляют названия роллов, а не ингредиенты, сами блюда уже есть в каталоге отдельно. Список в конфиге.
- **Уникальность:** уникальный индекс по нормализованному названию (регистр, `ё→е`, пробелы) плюс сопоставление через LLM.
- **Архивация категории:** автоматически, только если категория имеет происхождение `derived` и у неё не осталось активных позиций. Ручные категории не архивируются.
- Позиции хранятся так, чтобы при обновлении пересчитывались только изменившиеся.

**Реализация (этап 3).** Модули `catalog/taxonomy.py` (нормализация и seed), `ingredients.py` (разбор), `consolidate.py` (слияние дубликатов), `llm.py` (клиент модели).

- Разбор идёт пакетами по 12 позиций, до 4 запросов к модели параллельно, а запись в справочник строго по очереди под замком: иначе два пакета создавали бы одну категорию дважды. Группа в ответе модели указывается номером из списка в запросе (короче ответ, меньше ошибок).
- Ответ не по формату повторяется один раз. Обрезанный по длине или повторно битый ответ не повторяется, а пакет делится пополам (до трёх раз). Сбой одного пакета не останавливает остальные; его позиции остаются неразобранными и подхватываются при следующем обновлении.
- **Слияние дубликатов:** после разбора модель просматривает группы, где появились новые категории (по одной группе за запрос), и предлагает слияния. Код проверяет предложение (названия только из списка, ручные категории и группы не трогаются), переносит позиции в основную категорию, а название дубликата добавляет в её синонимы: при следующем разборе оно сразу сопоставляется с основной. Сбой слияния в одной группе не влияет на остальные.
- Ключ уникальности: слова названия по алфавиту без регистра, `ё→е` и знаков препинания («Сыр сливочный» = «Сливочный сыр»).
- Каталог считается готовым, когда есть успешная синхронизация и хотя бы одна активная категория; иначе при старте загрузка запускается заново. API: `GET /api/categories` (дерево групп с числом позиций).

**Результат на реальном каталоге (24.10.2026, `yandexgpt-5-pro/latest`).** 409 позиций, из них 76 (сеты, наборы, WOW price) пропущены. Первая версия без параллельности и слияния: 257 активных категорий, 13,5 минут, 16 позиций не разобрано. После доработки: **203 категории (191 выведенных и 12 ручных), весь первый запуск вместе с обходом сайта около 4 минут**, слито 25 дубликатов, напитки сведены к родовым названиям. Повторное обновление без изменений на сайте не обращается к модели (кроме неразобранных позиций) и занимает около 45 секунд.

**Известные недостатки автоматического черновика (до ручной правки, раздел 6а):** часть категорий лежит в неподходящих группах («Бобы эдамаме» в «Грибах», «Пицца Сырная» в «Крупах»); остаются близкие дубликаты («Рис» и «Рис для суши», «Панировочные сухари» и «Сухари панко»); слияние иногда объединяет слишком много («Томат» впитал варианты черри). Эти недостатки исправлены ручной правкой (раздел 6а): 203 → 176 категорий, группы и дубликаты приведены в порядок.

## 8. Локации

- Справочник лежит в репозитории файлами, а не в базе:
  - `locations/regions.json`: регион, список соседей по общей границе, идентификаторы для Yandex Search и 2GIS;
  - `locations/cities.json`: город, регион.
- В форме поиска: поле «Город / регион» с автодополнением по этим данным и переключатель «Включая соседние регионы». Поиск без выбора региона допускается.
- Агент получает список целевых регионов (выбранный + соседние, если включено).
- Бюджет: у крупных регионов бывает 6–10 соседей. Лимит шагов и числа запросов, приоритет у выбранного региона, затем соседи.
- Метка локации поставщика и её вес в ранжировании: в регионе → доставляет в регион → в соседнем регионе → неизвестно.
- **Риск:** составить и проверить справочник соседей — отдельная небольшая задача. Предлагается собрать из открытых данных и проверить вручную.

**Реализация (этап 4).** Модуль `app/locations/` (`regions.json`, `cities.json`, поиск и расширение на соседей), API `GET /api/locations?q=` (автодополнение) и `GET /api/locations/resolve?kind=&key=&neighbors=` (что выбрано и в каких регионах искать), компонент `LocationPicker` на странице.

- **Данные.** 89 субъектов РФ (список Росстандарта, как в Wikidata, включая ДНР, ЛНР, Запорожскую и Херсонскую области) и 1102 города. Регионы и общие границы взяты из Wikidata (CC0, свойство «имеет общую границу»), города с населением и координатами из hflabs/city (CC BY-SA 4.0, по Википедии). Сборка воспроизводима: `python -m scripts.build_locations`; загруженные данные кэшируются, результат лежит в репозитории. Обязательна ссылка на источники (она есть в самих файлах и в README); лицензия CC BY-SA распространяется на `cities.json`.
- **Соседи.** Граница взаимна (проверено тестом); из Wikidata получены 409 пар, вручную добавлена одна: Крым и Краснодарский край (мост и паром) — общей сухопутной границы нет, но для доставки это соседи. Калининградская область соседей не имеет. Названия республик приведены к официальным («Республика Татарстан» вместо «Татарстан»), короткие и разговорные названия («Питер», «ХМАО», «Кузбасс») ищутся как синонимы.
- **Проверка данных.** Тесты сверяют границы с общеизвестными фактами: у Свердловской области ровно 7 соседей, у Татарстана 8, у Адыгеи один (Краснодарский край), Приморский край граничит только с Хабаровским; все регионы, кроме Калининградской области, образуют одну связную сеть. На этапе сборки найден и устранён дубликат «Ялта» в исходных данных.
- **Поиск.** Нечувствителен к регистру и «ё»; порядок выдачи: полное совпадение, начало названия, начало слова, вхождение; регионы раньше городов, одноимённые города по населению, различаются регионом («Заречный · Пензенская область»).
- **Интерфейс.** Поле с автодополнением, выбор «Вся Россия» по умолчанию, переключатель «Включая соседние регионы» с перечнем регионов поиска. `expand()` отдаёт агенту выбранный регион первым и соседей по алфавиту.
- **Не сделано.** Идентификаторы регионов для Yandex Search и 2GIS не заполнены: ключи ещё не заведены, на этапе агента регион передаётся текстом в запросе. У четырёх новых регионов и у городов федерального значения города в справочнике отсутствуют (выбирается сам регион).

## 9. Агент

### Инструменты

| Инструмент | Что делает |
|---|---|
| `search_web(query, region)` | Yandex Search API |
| `search_places(query, city)` | 2GIS API |
| `fetch_page(url)` | Текст страницы в markdown + список ссылок на «контакты», «доставка», «прайс», «о компании» |
| `save_supplier(...)` | Сохраняет поставщика с полями, цитатами и источниками; поле без валидной цитаты отклоняется |
| `research_suppliers(sites)` | Полное изучение до трёх сайтов за вызов (см. «Реализация (этап 9а)») |
| `finish(summary)` | Завершает работу |

### Ограничения (в коде, а не в промпте)

- Максимум шагов, запросов и время на запуск; таймауты инструментов.
- Дедупликация поставщиков по домену и по ИНН.
- Проверка цитаты: фрагмент должен реально присутствовать в тексте страницы.
- Валидация телефона, email, ИНН (контрольная сумма), доступности домена.
- Отсев агрегаторов, маркетплейсов и каталогов-перепродавцов (список в конфиге).
- Если данных нет, поле остаётся пустым.
- Кэш загруженных страниц, чтобы повторные запуски не ходили в сеть.

**Реализация (этап 9а): полнота данных по ТЗ.** В ТЗ обязательны название, сайт и источник, контакты, чем занимается, а «плюсом» регион работы, минимальный заказ, цена, сертификаты, условия доставки. Живые запуски показали, что модель сама редко доходит дальше главной и контактов, поэтому обход сайта вынесен в код (`agent/research.py`, `ToolBox._research_supplier`), а модель только извлекает поля:

1. Код открывает главную и по одной лучшей ссылке на каждый раздел (контакты, о компании, доставка и оплата, прайс и каталог, сертификаты).
2. Одним запросом к модели из текстов страниц извлекаются поля со ссылкой на страницу и дословной цитатой. Каждое поле проходит те же проверки `save_supplier`: цитата есть на странице, значение следует из цитаты (числа и не менее половины значимых слов), телефон и ИНН прошли проверку формата; одинаковые цитаты не сохраняются дважды.
3. Если каких-то полей не хватает, код делает запросы `site:домен …` по темам (минимальный заказ и цены, сертификаты, доставка и регионы, адрес), открывает найденные страницы и извлекает недостающее (второй проход).
4. В карточке показывается, сколько страниц сайта изучено и каких полей на сайте нет («не найдено на сайте»).

Сайт, который не открылся (таймаут, обрыв, TLS), не ломает запуск: в ленте появляется событие «Не открылся», модели возвращается результат с причиной, повторно этот сайт не открывается. Токены, потраченные внутри изучения, входят в общий бюджет запуска. **Гарантия честная и ограниченная:** код гарантирует, что страницы всех разделов и поиск по сайту по недостающим темам выполнены; если на сайте поставщика данных нет (например, цены только по запросу), поле остаётся пустым, ничего не выдумывается. Контрольный запуск «Моцарелла», Казань: 3 поставщика, ~35 тыс. токенов (~16 ₽); у одного найдены все поля (кроме телефона), у других цены и сертификатов на сайте нет, один сайт не открылся.

Лимиты по умолчанию подняты ради полноты и сокращено число запусков: 24 шага, 600 секунд, 200 тыс. токенов (до ~240 ₽ в худшем случае), 70 загрузок страниц (было 45: в прогоне eval лимит кончался в 2 случаях из 3), 10 запусков в сутки.

**Реализация (после ревью).** Исправлены слабые места, найденные при ревью агента:

- **Проверка значения по цитате.** Раньше у названия, типа поставщика и коротких описательных полей (до трёх значимых слов) сверялись только числа, поэтому «Татарстан» проходил с цитатой «Москва и область», а «производитель» — с цитатой «Контакты». Теперь все слова короткого значения должны быть в цитате (с поправкой на падежи), длинного — не меньше половины; единицы при числах (кг, руб, шт, %) должны совпадать; у названия не учитываются ООО, ТД и подобное; тип поставщика должен быть назван в цитате («производство», «опт», «дистрибьютор»); цитата короче 5 символов не принимается. Старые поля проверяются по тем же правилам при выдаче.
- **Отсев кандидатов.** Перед подробным изучением короткий запрос к модели по главной странице и отрывку из выдачи (около 1 тыс. токенов): продаёт ли компания нужный продукт бизнесу. При явном «нет» или при «неясно» по обоим вопросам сайт не изучается и не сохраняется; если неясен один ответ или проверка не удалась, сайт изучается, а сбой записывается в `qualification.error`. В лимит изучаемых сайтов идут только подробно изученные. Итог проверки хранится в `suppliers.research.qualification` и показан в карточке.
- **Регион в Яндекс Поиске.** Параметр `region` запроса Search API v2; коды в `locations/yandex_regions.json` из таблицы документации (60 городов, в основном столицы регионов; у региона код его столицы; без кода — Россия, 225). Поиск по сайту поставщика (`site:`) идёт без региона.
- **Надёжность изучения.** Обрезанный по длине ответ при извлечении делится на две половины страниц, а его токены учитываются в расходе (раньше сайт падал целиком, а расход занижался). Таймаут 180 с на каждый сайт, а не на пачку из трёх: медленный сайт не отменяет остальные и повторно не изучается. Сайт без подтверждённых названия и контакта не добирается поиском по сайту. За вызов изучается не больше сайтов, чем не хватает до цели. Отказ в раннем `finish` в режиме изучения предлагает `research_suppliers`, а не недоступный `fetch_page`. Сбой модели после сохранённых поставщиков завершает запуск со статусом `done`, а не `failed`.
- **Повторное использование.** Поставщик, подробно изученный за последние 7 дней (`Limits.reuse_days`), привязывается к новому запуску из базы без нового извлечения.
- **Текст страниц.** Меню навигации (`<nav>`) не попадает в текст, но подписи его ссылок остаются для выбора разделов; начало страницы в тексте для модели сокращено с 900 до 500 символов.
- **Неизменность истории.** У поля хранится запуск, где оно найдено впервые (`supplier_fields.first_run_id`, миграция 0007); результаты запуска показывают только поля этого и прошлых запусков. Более полная запись адреса из нового запуска добавляется рядом, а не заменяет прежнюю.
- **Лимиты и выкладка.** Проверка суточного лимита и числа идущих запусков и создание запуска идут под advisory-блокировкой. Выкладка ждёт окончания идущих запусков (до 12 минут).
- **По итогам первого прогона eval** (3 случая, 26.10.2026, 270 ₽; отсев не отклонил ни одного из ~17 сайтов, лимит загрузок кончался в 2 случаях из 3):
  - поставщик с подтверждённым телефоном или email, но без подтверждённого названия сохраняется под доменом, а не отбрасывается (Оптиком и Pack-Craft пишут название не так, как его записала модель); подтверждённое позже название заменяет домен;
  - выбранный город называется в запросе агента (раньше передавался только регион, и запросы шли со словами «Республика Татарстан» вместо «Казань»);
  - отсев строже (см. выше), лимит загрузок страниц 45 → 70;
  - адрес «г. Казань обслуживается через филиал г. Тула…» даёт метку «Доставляет в ваш регион», а не «В вашем регионе»;
  - eval сохраняет вердикты проверки всех сайтов, причины отказов и отклонённых полей и выводит их в `score`; в статистике запуска появились `rejected` и `reused`.
- **Измерение качества.** `backend/scripts/eval/`: 12 случаев «продукт × место», платный прогон агента без базы приложения, ручная разметка `labels.csv`, метрики (точность, доля в регионе, полнота ключевых полей, ₽ за релевантного поставщика). На настоящей модели ещё не прогонялся.

## 10. Данные

- `catalog_syncs`: id, запуск (`startup`/`manual`), статус, время, счётчики, признак неполного обхода, ошибка.
- `items`: `source_id` (уникален), название, раздел, описание, статус, в какой синхронизации замечена.
- `categories`: название, нормализованное название (уникально), родитель, группа, синонимы, происхождение (`derived`/`manual`), статус.
- `item_categories`: связь позиции и категории.
- `runs`: id, категория, локация, флаг соседей, статус, времена.
- `run_events`: события агента (тип, полезная нагрузка, время).
- `suppliers`: домен (уникален), название, ИНН, заметка закупщика (`note`).
- `supplier_fields`: поставщик, поле, значение, `source_url`, цитата, уверенность, время проверки.
- `run_suppliers`: запуск, поставщик, балл, ранг, метка локации, объяснение.
- `fetched_pages`: URL, время, хеш, текст (кэш).

## 12. Интерфейс

1. **Загрузка каталога** (при первом запуске): прогресс по городам.
2. **Поиск:** категория, локация, переключатель соседних регионов, фильтр типа.
3. **Запуск:** живая лента шагов и карточки поставщиков, появляющиеся по мере готовности.
4. **Результаты:** список с рангом, метками локации и объяснением; блок «Рекомендуем связаться»; выбор 2–4 для сравнения.
5. **Сравнение:** таблица бок о бок.
6. **Заметка** в карточке поставщика и строка «Заметка» в сравнении.
7. **Справочник:** категории и позиции меню (обновление каталога из приложения отключено, см. раздел 6а).

**Реализация (этап 6).** Интерфейс разделён на две вкладки: «Поиск» и «Справочник» (категории и позиции меню). Адрес запоминает открытый запуск: `#search/3`, `#catalog`; ссылку на запуск можно сохранить и открыть позже.

- **Форма поиска:** выбор категории из справочника с автодополнением (по названию и синонимам), локация (город или регион, переключатель «Включая соседние регионы»; по умолчанию «Вся Россия»), тип поставщика (любой, производитель, дистрибьютор, оптовик), кнопка «Найти поставщиков» с пометкой, что запуск платный (обычно 70–100 ₽, не больше ~250 ₽).
- **Живая лента:** `GET /api/runs/{id}/stream` (SSE) отдаёт события запуска. Источник — таблица `run_events`, поэтому лента переживает обновление страницы и перезапуск приложения; при обрыве браузер сам переподключается с `Last-Event-ID` и получает только новые события (клиент дополнительно отбрасывает повторы по номеру). Завершённый запуск проигрывается из базы без обращения к модели, в конце приходит `stream_end` со статусом. Через Caddy поток идёт без буферизации.
- **Ход запуска:** статус («Идёт поиск…», «Завершён», «Не удалось»), счётчики (поисков, открытых страниц, найденных поставщиков), лента шагов с типами (поиск, страница, сохранён, отклонено, итог), итог с причиной остановки и расходом токенов.
- **Карточки поставщиков** появляются по мере сохранения: название, сайт, тип, телефоны, email, адрес, описание и остальные поля. У каждого значения можно раскрыть «источник»: дословную цитату, страницу, дату проверки. У ИНН есть ссылка на проверку в реестре.
- **История запусков** (последние 15) открывается без новых платных обращений.
- **Что проверено без платных запросов:** лента и карточки вживую на запусках с подставной моделью (на ту же базу и тот же API), воспроизведение реального запуска №3, отказ формы при занятых слотах (429: «Уже идут другие запуски»). В ходе проверки найдена и исправлена гонка: два одновременных запуска, нашедших одного нового поставщика, могли столкнуться на уникальном домене; сохранение одного домена теперь идёт под advisory-блокировкой (тест падает без неё).
- **Не проверено вживую:** старт реального запуска из формы (платный; запрос формы проверен до ответа 429, а запуск по тому же API делался вручную на этапе 5).

**Реализация (этап 7).** Модуль `app/ranking/` (`places.py` — регион по тексту, `scoring.py` — баллы и объяснение), `GET /api/runs/{id}/suppliers` теперь отдаёт поставщиков по рейтингу с блоком `ranking` и списком `recommended_ids`. Оценка считается при чтении по сохранённым полям, поэтому всегда соответствует текущим данным.

- **Решение: без модели.** По ТЗ объяснение мог формировать LLM; сделано кодом по шаблонам. Причины: каждый пункт объяснения опирается на сохранённое поле с цитатой (нечего выдумывать), результат стабилен и покрыт тестами, ранжирование бесплатно (запуски с моделью уже стоят денег). Минус: формулировки шаблонные.
- **Баллы (из 100):** совпадение с продуктом 20 (упоминание в описании или ассортименте 20, в названии 15, иначе 8); расположение 30; полнота данных 25 (вес полей: телефон 5, email 2, адрес 2, тип 1, описание 1, ассортимент 1, регионы 2, доставка 3, минимальный заказ 3, цены 3, сертификаты 2: больше всего весят телефон и условия закупки, а не тексты о компании); надёжность 15 (ИНН с проверенной контрольной суммой 8, два способа связи 4, данные подтверждены хотя бы двумя разными страницами 3); тип поставщика 10 (совпал с искомым или тип не важен 10, на сайте не указан 4, другой 0). При равной оценке выше тот, кто ближе, затем у кого полнее данные, затем по названию.
- **Метки расположения** относительно основного региона поиска: «В вашем регионе» (адрес в регионе, 30; если в адресе регион не назван, как у «пгт Рыбная Слобода», регион берётся из описания компании), «Доставляет в ваш регион» (регион назван в регионах поставки или условиях доставки, 26), «В соседнем регионе» (адрес в регионе-соседе, 18), «Заявляет доставку по России» (общее «по всей России» без названия региона, 14), «Регион неизвестен» (10), «В другом регионе» (адрес в чужом регионе или перечислены регионы поставки без нашего, 2: ниже «неизвестно», потому что у такого поставщика уже есть баллы за заполненный адрес). Если локация не выбрана, всем одинаково по 15, метка «Вся Россия».
- **Регион по тексту** (`places.py`): шаблоны по основам слов с падежами («Татарстану», «в Казани»); уличные названия не принимаются за города («Тверская», «Казанская», «Московский проспект»); области и края распознаются только вместе со словом «область», «край», «обл.»; крупные города (от 100 тыс.) и все города региона поиска и его соседей определяют регион. Проверено на таблице случаев в тестах.
- **Объяснение:** «почему подходит» (факты из полей), «нет данных» (минимальный заказ, цены, доставка, регионы, сертификаты, ИНН, адрес) и «что уточнить» (вопросы для звонка, например «Узнайте, доставляют ли в регион «Республика Татарстан» и на каких условиях»).
- **Рекомендация «с кем связаться»:** первые три поставщика с оценкой не ниже 40 из 100, у которых есть телефон и тип не противоречит искомому (без телефона звонить некуда); если таких нет, показывается пояснение.
- **Смысловые проверки полей** (`validation.fact_problem`, при сохранении и при выдаче старых запусков): сумма заказа для бесплатной доставки не принимается за минимальный заказ; цена принимается, только если искомый продукт назван в цитате, рядом с ней на странице или в заголовке страницы (цена на сливочное масло в поиске моцареллы отклоняется). «Не найдено на сайте» считается при выдаче по нынешним полям, телефон обязателен и при найденном email.
- **Предупреждение об аналоге:** если в названии, описании, ассортименте или ценах есть «заменитель молочного жира», «СЗМЖ», «молокосодержащий», «сырный продукт» или «растительный жир», карточка показывает предупреждение и первым вопросом для звонка просит уточнить, натуральный ли продукт.
- **Сравнение 2–4 поставщиков** таблицей бок о бок (оценка, расположение, все поля; отсутствующие данные подсвечены «нет данных»). Выбор галочками в карточках; считается на клиенте по уже загруженным данным.
- **Результат на реальном запуске №3** («Моцарелла», Казань): «Инлут» 72/100 (в вашем регионе, рекомендован), «Гурман» 45 (регион неизвестен, рекомендован), GFC 39 (не рекомендован: нет адреса, телефона и подтверждённых данных). Агент теперь просят искать адрес и регионы доставки (поправка в промпте; на настоящей модели не проверялась).
- **Ограничения:** расположение определяется только по полям `address`, `regions`, `delivery_terms`, `description`, которые собрал агент; если их нет, метка «Регион неизвестен» (телефонные коды городов не используются: нет справочника). Веса оценки заданы мной и не калибровались на реальных предпочтениях закупщика.

## 13. Проверка моделей и открытые вопросы

**Проверка моделей (первый шаг, 1–2 часа):** пробный сравнительный прогон, чтобы выбрать модель до начала основной разработки. Это одноразовый скрипт, не часть сервиса. Одна и та же задача («найди 3 поставщиков сыра в Казани, извлеки поля с цитатами») с заглушками инструментов прогоняется несколько раз на каждой модели. Сравниваем: корректность вызовов инструментов и аргументов, валидность JSON по схеме, наличие цитат, качество русского языка, время и токены. Результат — короткая таблица и выбор модели.

Реализация: `backend/scripts/model_check/`. Три сценария: (1) агентный цикл с инструментами-заглушками (поиск, загрузка страницы, сохранение поставщика с цитатой), (2) извлечение полей поставщика со страницы с цитатами, где одно поле намеренно отсутствует в тексте (проверка на выдумывание), (3) извлечение ингредиентов из описаний блюд eda1.ru. Каждый сценарий повторяется несколько раз для оценки стабильности. Запуск из каталога `backend`: `python -m scripts.model_check.run --provider yandex --runs 3`; если нативные вызовы функций не работают, добавить `--tool-mode json` (запасной режим JSON-действий).

**Результаты: Yandex AI Studio (24.10.2026, 3–5 прогонов на сценарий).** Все модели получили `tools`-вызовы через Chat Completions по адресу `https://ai.api.cloud.yandex.net/v1`.

| Модель | Инструменты | Извлечение с цитатами | Ингредиенты | Время (инстр./извл./ингр.), с |
|---|---|---|---|---|
| `yandexgpt-5-pro/latest` | 3/3 | 5/5 | 3/3 | 5.7 / 10.9 / 4.5 |
| `yandexgpt/rc` | 3/3 | 5/5 | 3/3 | 3.9 / 2.5 / 1.3 |
| `aliceai-llm/latest` | 3/3 | 5/5 | 3/3 | 6.7 / 10.6 / 4.8 |
| `yandexgpt-lite/latest` | 0/3 (отвечает текстом) | 0/5 (не даёт цитат) | 3/3 | 1.9 / 5.3 / 3.3 |
| `yandexgpt-4-lite/latest` | не поддерживает `tools` (ошибка API) | 0/3 | 3/3 | — |

Выводы: Lite-модели для агента не подходят (не вызывают инструменты, игнорируют формат цитат). Три остальные справляются с набором сценариев одинаково; различие только в скорости. Сценарии намеренно простые (короткая страница, одна цель), поэтому они отсеивают слабые модели, но не выбирают лучшую среди сильных. Окончательное сравнение будет на реальных страницах в ядре агента.

**Нужно от вас:**
- ключи Yandex Cloud (AI Studio и Search API), GigaChat (если участвует в сравнении), позже 2GIS: вносятся в файл `.env` (раздел 17).

**Открытые вопросы:**
- Поддерживает ли выбранная модель нативный tool calling (проверяет проверка моделей).
- Содержит ли страница раздела eda1.ru все позиции с описаниями; стабильны ли id (проверка в начале этапа 2).
- Тарифы Yandex Search API и 2GIS (уточняем при заведении ключей).
- Источник данных для справочника регионов и соседей.

## 16. Риски

- Качество модели и стабильность tool calling: снимает проверка моделей, запасной вариант — JSON-действия.
- Сайты поставщиков на JS или с защитой от ботов: опциональный `playwright`, остальное фиксируем как «нет данных».
- Выдуманные данные: защита — обязательная цитата с программной проверкой.
- Стоимость и время запуска: лимиты шагов, кэш страниц, дешёвая модель на массовых шагах.
- Условия использования eda1.ru: берём только публичные страницы меню, названия и описания позиций, с паузами; данные нужны для построения справочника ингредиентов, не для перепубликации.
- Справочник соседей регионов: готовых данных нет, нужна ручная проверка.

## 17. Секреты и конфигурация

- Все ключи и пароли хранятся в файле `.env` в корне репозитория. Шаблон со всеми переменными лежит в `.env.example`: его копируют в `.env` и заполняют. Настоящий `.env` не попадает ни в репозиторий (`.gitignore`), ни в Docker-образы (`.dockerignore`).
- В Docker Compose переменные передаются в контейнер через `env_file`, файла `.env` внутри образа нет.
- Настройки загружает `backend/app/config.py` (pydantic-settings): типизированно, с одним объектом настроек на всё приложение. Секреты имеют тип `SecretStr`, поэтому не попадают в логи и `repr`.
- Приложение стартует и без ключей: например, загрузка каталога их не требует. Там, где ключ нужен, код вызывает `settings.require("LLM_API_KEY", ...)` и получает понятную ошибку со списком недостающих переменных.
- Переменные: адрес и параметры базы; `YANDEX_CLOUD_FOLDER_ID`; `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` (Yandex AI Studio); `GIGACHAT_CREDENTIALS`, `GIGACHAT_SCOPE`, `GIGACHAT_MODEL`, `GIGACHAT_CA_BUNDLE` (путь к сертификатам НУЦ Минцифры: серверы GigaChat подписаны ими, а Python им по умолчанию не доверяет; файл `certs/russian_trusted_ca.pem` в репозитории, это публичные сертификаты, не секрет); `YANDEX_SEARCH_API_KEY`; `DGIS_API_KEY`; параметры обхода сайта (`CRAWL_DELAY_SECONDS`, `CRAWL_USER_AGENT`).
- Для продакшна секреты стоило бы вынести в менеджер секретов; для тестового задания `.env` достаточно (отражается в README).
